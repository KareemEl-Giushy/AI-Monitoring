A runaway agent doesn’t crash. It keeps going.

Autonomous agents fail by repeating themselves. Every request looks valid on its own, so nothing errors and nothing alerts, while the tokens keep flowing until someone reads the bill.

  • CB-01

    Tool loops with mutated arguments

    The agent runs the same search again with “(attempt 1)”, then “(attempt 2)”. Each call is slightly different, so each one looks like new work.

  • CB-02

    Retry and error storms

    A tool keeps failing and the agent keeps calling it, feeding each failure back into the next attempt.

  • CB-03

    Degenerate output

    The model collapses into repetitive, low-information text such as “! ! ! !” and keeps generating it.

  • CB-04

    Endpoint hammering

    A tight loop fires requests at one endpoint far faster than any person would.

  • CB-05

    Silent token burn

    None of the above raises an error, so spend climbs quietly in the background.

Why rate limiters and exact-hash dedupe miss it

Rate limiter

Counts requests, not behavior. A loop running at a steady pace stays under the limit forever, while a legitimate burst of work gets throttled.

Exact-hash dedupe

Change one character and the fingerprint is unrelated, so the loop looks like fresh work.

  • …crashloop fix (attempt 0)
    sha256 436ada7dc45f…
  • …crashloop fix (attempt 1)
    sha256 dd1fc3c6b2dd…

AI Agent Circuit Breaker

Compares what the agent is doing. The same two calls share most of their character 3-grams, so they count as one repeated action.

One proxy between your agents and the model API

Point your agent’s base URL at the breaker proxy instead of the model API. It forwards every path and query unchanged to the LiteLLM gateway, which routes each request to Groq, Gemini or Ollama. LiteLLM’s metrics flow into Prometheus and Grafana.

What happens to every request

  1. Identify the sessionFrom the X-Session-ID header, else the Authorization header, else the client IP.
  2. Check velocity firstBefore the body is even read. Too many requests per second, or too many hits on one endpoint, returns 429 with VELOCITY_BLOCKED.
  3. Parse the OpenAI bodyModel, messages and tool calls are read, and the body is restored untouched for forwarding.
  4. Scan the conversation historyLooping tool calls, piled-up tool errors and low-entropy text return 429 with OPEN_TRIPPED before the model is called.
  5. Record the sliding windowRequests, estimated tokens and models over the last 60 seconds. With -enforce-limits, an over-budget request gets 429.
  6. Forward upstreamPath and query intact, X-Forwarded-For added. If the upstream is down, the agent gets a JSON 502.
  7. Inspect the response as it arrivesEvery byte feeds the entropy engine and streamed tool-call fragments are reassembled. A trip closes the upstream stream and appends the incident.
  8. Write the audit trailEach turn is saved to a conversation JSON file, grouped by client IP.

Five breakers on one panel

Each detector watches for one way an agent runs away. Every threshold below is the shipped default and can be changed with a flag, an environment variable or config.yaml. Flip a lever to see what that breaker reports when it trips.

  • CB-01
    CLOSED

    Tool-call loop

    The same tool called again and again with near-identical arguments. Arguments are normalized, then compared by character 3-gram Jaccard similarity; free-form text arguments are also compared by 64-bit SimHash.

    Trips at
    The 3rd similar call: Jaccard ≥ 0.85, or SimHash ≤ 3 bits apart
    Reports
    TOOL_CALL_REPETITION_LOOP
  • CB-02
    CLOSED

    Tool error accumulation

    A failing tool the agent keeps retrying. Tool results in the conversation are scanned for error signs such as tracebacks, “permission denied” or “timed out”.

    Trips at
    4 tool errors in one conversation
    Reports
    TOOL_ERROR_ACCUMULATION
  • CB-03
    CLOSED

    Stream entropy

    Degenerate, repetitive output like “! ! ! !”. Shannon entropy in bits per byte, measured on message content, tool arguments and the response stream.

    Trips at
    Below 1.5 bits/byte, once there are 64 bytes of text or 30 bytes of tool arguments
    Reports
    MODEL_DEGENERATION_LOW_ENTROPY
  • CB-04
    CLOSED

    Session velocity

    A tight loop hammering the API. Requests are counted per session over a rolling one-second window, and hits per endpoint over ten seconds.

    Trips at
    More than 5 requests in 1 s, or more than 20 hits on one endpoint in 10 s
    Reports
    VELOCITY_MAX_RPS_EXCEEDED
    VELOCITY_MAX_ENDPOINT_REPEATS_EXCEEDED
  • CB-05
    CLOSED

    Sliding-window budget

    Silent token burn. Tracks requests, estimated tokens (about 4 characters per token) and models over a rolling 60-second window, shown live in the terminal dashboard.

    Trips at
    Your request or token limit, with -enforce-limits on. Limits default to 0 (unlimited).
    Reports
    token limit exceeded in sliding window

What about SimHash? It isn’t recomputed here. The proxy splits the tool name and arguments into words, hashes each word with 64-bit FNV-1 and folds them into a 64-bit fingerprint; two calls whose fingerprints differ in 3 bits or fewer count as similar. SimHash decides for free-form text arguments. For JSON arguments, the normal case for OpenAI tool calls, Jaccard alone decides.

Every trip comes with an incident report

The agent, and whoever is on call, gets a structured SRE incident instead of a silent failure: what tripped, which calls caused it, and what to do next.

429 At the edge
When the history check or the velocity detector trips, the request never reaches the model. The agent gets 429 Too Many Requests, a Retry-After header (10 s for breaker trips, 5 s for velocity) and the incident as JSON.
SSE Mid-stream
When a live streamed response trips a breaker, the proxy closes the upstream stream and appends an event: error frame carrying the same incident, instead of [DONE]. The status stays 200 because the headers were already sent.
  • failure_class names the breaker that tripped.
  • violating_calls lists the calls behind it, with similarity and entropy.
  • mitigation and action_required say what happened and what to fix.

Prevention in the proxy, visibility in Grafana

The circuit breaker stops a runaway agent while it’s happening. The observability stack shows what your agents cost and how each model behaves over hours and days.

Prevention: circuit breaker proxy

Acts on the request in flight. Blocks loops, error storms, degenerate output and runaway velocity, and returns an incident the agent can act on.

Visibility: observability stack

Records every call that reaches the gateway. Latency, time to first byte, spend, tokens, errors and failed fallbacks, per model.

The stack

  • LiteLLM:4000One OpenAI-compatible endpoint and one master key for every model. Exports Prometheus metrics and keeps spend logs in Postgres.
  • Prometheus:9090Scrapes LiteLLM’s /metrics every 5 seconds.
  • Grafana:3000Starts with the Prometheus data source already provisioned. Import the LiteLLM dashboard from 24965_rev2.json.

Run it locally

The proxy is a single Go binary. The observability stack is one docker compose file. Run either on its own, or chain them.

Circuit breaker proxy

Needs Go 1.26 or newer. go.sum isn’t committed, so run go mod tidy once after cloning.

shell
git clone https://github.com/KareemEl-Giushy/AI-Ciurcit-Breaker.git
cd AI-Ciurcit-Breaker
go mod tidy
go build -o proxy-server main.go
./proxy-server -port 8080 -target http://localhost:4000
  • Point your agent at http://localhost:8080/v1.
  • Always pass -target: the default is http://localhost:3000, which is Grafana in the observability stack.
  • Add -show-sliding-window for the live terminal dashboard.
tests
go test ./...
go test -race ./...
go vet ./...
go test -bench=BenchmarkEntropy -benchmem ./inspector

Observability stack

Needs Docker with Compose, plus API keys for the providers you plan to use.

shell
git clone https://github.com/KareemEl-Giushy/AI-Monitoring.git
cd AI-Monitoring
cp .env.example .env
# edit .env: set GROQ_API_KEY, GEMINI_API_KEY, OLLAMA_API_KEY
# and replace LITELLM_MASTER_KEY (it must start with "sk-")
docker compose up -d
docker compose ps
  • LiteLLM: http://localhost:4000 (admin UI at /ui)
  • Prometheus: http://localhost:9090
  • Grafana: http://localhost:3000, sign in with admin / admin and change the password.
  • In Grafana, open Dashboards, then New, then Import, upload 24965_rev2.json and pick the Prometheus data source. Panels fill in after the first requests.

Full chain

Agent → Circuit Breaker :8080 → LiteLLM :4000 → providers. Start the stack, put the proxy in front of it, then call a model through the proxy.

shell
# Terminal 1: gateway + observability
cd AI-Monitoring && docker compose up -d

# Terminal 2: circuit breaker proxy in front of LiteLLM
cd AI-Ciurcit-Breaker
./proxy-server -port 8080 -target http://localhost:4000

# Terminal 3: call a model through the proxy
export LITELLM_MASTER_KEY=sk-1234   # use the value from your .env
curl -sS http://localhost:8080/v1/chat/completions \
  -H "Authorization: Bearer $LITELLM_MASTER_KEY" \
  -H "Content-Type: application/json" \
  -H "X-Session-ID: demo-agent-1" \
  -d '{"model":"qwen3.6-27b","messages":[{"role":"user","content":"Say hello in five words."}]}'

Watch a breaker trip without spending tokens: ten parallel requests on one session. The first five pass and the rest come back 429 with VELOCITY_BLOCKED.

shell
seq 1 10 | xargs -P10 -I{} curl -s -o /dev/null -w "%{http_code}\n" \
  http://localhost:8080/v1/models \
  -H "Authorization: Bearer $LITELLM_MASTER_KEY" \
  -H "X-Session-ID: burst-demo"

Give each agent its own X-Session-ID. Without it, every agent sharing the master key shares one velocity budget.
